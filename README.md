# Cloud Workload Forecasting (Azure VM trace)

Forecasts the final two hours (24 five-minute timestamps) of two fleet-level series built from a
curated subset of the [Azure Public Dataset V2](https://github.com/Azure/AzurePublicDataset):

- `active_vm_count`: number of VMs with a reading at each timestamp
- `aggregate_cpu_utilization`: mean of the VMs' average CPU (%) at each timestamp

The full analysis, validation and capacity-planning recommendation are in
[`reports/final_report.pdf`](reports/final_report.pdf) (same content in `reports/final_report.md`).

## Key findings

- The fleet is stable and lightly loaded: average CPU about 9.4% (standard deviation 0.19 points).
  `active_vm_count` is constant at 10,000 in this subset, so persistence forecasts it exactly.
- Persistence (repeat the last observed value) was selected as the final model. Over rolling
  24-step forecasts in the training window its MAE is 0.23 and its RMSE is 0.29 CPU points.
- Tuned SVR, Random Forest, AdaBoost and XGBoost models (Optuna, time-ordered validation) did not
  clearly beat it. When tuned without seeing the test block, the best SVR was only 3.3% better, which is within noise.
- Recommended policy: provision for the forecast plus a margin of 0.41 CPU points (90%) or
  0.50 points (95%), and watch the busiest VMs and the Interactive category separately.

## Installation

Python 3.9 or newer (developed on Python 3.12).

```bash
python -m venv .venv
source .venv/bin/activate        # Windows: .venv\Scripts\activate
pip install -r requirements.txt
pip install -e .
```

`requirements.txt` also lists the notebook libraries (matplotlib, seaborn, scikit-learn, optuna,
xgboost). The prediction command itself needs only pandas and numpy.

## Dataset

The data is not committed to this repository. Extract the `data-v1` release supplied with the
assignment into `challenge_data/` at the repository root:

```text
challenge_data/
├── vm_cpu_readings.csv.gz
├── vm_metadata.csv.gz
├── DATA_CARD.md
└── SHA256SUMS
```

Optional integrity check: `cd challenge_data && sha256sum -c SHA256SUMS`.
The loader accepts `vm_cpu_readings.csv.gz` or `vm_cpu_readings.csv`.

## Generate the predictions

```bash
python -m forecast.predict --data challenge_data --output predictions.csv
```

| Option | Default | Meaning |
|---|---|---|
| `--data` | `challenge_data` | folder containing `vm_cpu_readings.csv(.gz)` |
| `--output` | `predictions.csv` | file to write |
| `--horizon` | `24` | number of final timestamps to forecast |

The command prints `wrote predictions.csv (24, 3)`. The file has the columns
`timestamp,active_vm_count,aggregate_cpu_utilization` and no index column. Before writing, it checks
that there are exactly 24 rows, unique timestamps in chronological order, finite values,
`active_vm_count >= 0` and `aggregate_cpu_utilization` within [0, 100], and it stops with an error otherwise.
The command has no randomness, so repeated runs give identical files.

The holdout is always the final 24 timestamps of the supplied data. Only their timestamps are read.
Their target values are never used, and nothing depends on the number of VMs or timestamps in the data.

## Tests

```bash
pytest
```

The tests cover the target construction (each VM counted once, invalid readings ignored), the output
contract, that changing the holdout values does not change the predictions, that the final timestamps
come from the raw data, and the full command on a tiny dataset.

## Notebooks

The analysis notebooks were written in Google Colab. Before running them locally, change the paths in
the `read_csv` calls at the top to `challenge_data/vm_cpu_readings.csv.gz` and
`challenge_data/vm_metadata.csv.gz`. They cover the data checks, the workload analysis, the
Optuna comparison of models and the error analysis. Optuna uses `TPESampler(seed=42)`, and Random Forest and
AdaBoost use `random_state=42`.

## Method in brief

1. **Targets.** Built per timestamp from the VM readings. Duplicate (`vm_id`, `timestamp`) rows are
   dropped, readings with a missing or out-of-range `avg_cpu` are ignored, and no value is invented for
   a missing timestamp.
2. **Split.** The first 110 timestamps are the training window and the last 24 are the holdout, using
   `iloc[:-24]` and `iloc[-24:]`.
3. **Validation.** Time-ordered only, never shuffled: `TimeSeriesSplit` with 24-step test blocks, and
   a 24-step recursive forecast on a block inside the training window. Thresholds and margins use
   training rows only.
4. **Models compared.** Persistence and the historical mean as baselines, against Random Forest,
   AdaBoost, XGBoost and SVR on six lagged values, tuned with Optuna.
5. **Decision.** Persistence, because no tuned model was clearly better when evaluated fairly.

## Limitations

- The data covers about 11 hours, so daily or weekly seasonality cannot be assessed.
- The subset keeps only VMs with complete observations, so it cannot show real VM churn.
- Model comparisons rest on one 24-point block and about 100 training rows, so small differences are noise.
